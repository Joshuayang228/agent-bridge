### [已作废·桌宠方向] 2026-07-04 选题：做「有 agent 大脑的桌面伙伴」（桌宠）
**背景**：Trae 大赛参赛作品从零选题。候选方向来自现有项目积累——my-agent（人格化桌面 AI Agent）和 AI电商。需要一个既能发挥已有优势、又有 Demo 冲击力、还契合个人产品理念的方向。
**决策**：做桌宠形态的桌面 AI 伙伴——一个会动、有情绪、能主动搭话的桌面角色，背后接 my-agent 的完整 agent 引擎。
**原因**：
1. 不是从零起步——my-agent 已完成 Agent Loop / 向量记忆 / 人格模板 / 语音 IO / 后台常驻 / 20 内置工具 / 多 Provider 路由，桌宠是给成熟引擎加"活的表现层"，工作量与风险都可控。
2. Demo 冲击力强——评审看惯 chatbot/RAG/coding assistant，屏幕上一个活的角色第一眼就记得住，是关系型 AI 唯一能被"看见"的形态。
3. 契合产品哲学——my-agent 定位"数字伙伴而非命令式工具"、roadmap Phase 3 的"活人感/具名角色设定集"，桌宠是这些理念第一次长出身体。
**赢点定位**：不靠萌画风取胜（遍地都是），杀手锏是"有真正 agent 大脑的桌面伙伴"——长期记忆、能调工具、人格进化、感知上下文主动开口。这是 my-agent 的深度 × 桌宠的形态，别人没这套引擎抄不走。
**放弃的选项**：AI电商——业务探索方向，Demo 观感弱、与个人技术优势结合度低，不适合比赛短周期高冲击的诉求。

### 2026-07-04 代码策略：fork my-agent 整仓，而非新起壳复用引擎
**背景**：桌宠要复用 my-agent 引擎，有两条路——fork 整个仓库改表现层，或新建项目只抽引擎。
**决策**：fork my-agent 整仓，在其上改造表现层。
**原因**：my-agent 的引擎（loop/记忆/人格/工具）与 UI 深度耦合，"只抽引擎"要反向拆一遍依赖，得不偿失。依赖是纯 Web 栈（React 19 + Vite + sql.js WASM，无原生编译模块），fork 后 npm install 基本可直接跑，无雷。
**认清的代价**：fork 那刻起 trae大赛 与 my-agent 分叉成两条命，my-agent 后续的 bug 修复与 M6–M10 模块不会自动流过来。但比赛要的是某时间点的完整交付而非长期维护，可接受——fork 后 my-agent 是"素材库"不是"上游"。
**已识别的改造点**：(1) 窗口改根——从标准带边框窗口改为透明/无边框/置顶/可点击穿透（electron/main/index.ts 的 createWindow）；(2) 双窗口架构——桌宠常驻小窗 + 唤起完整聊天窗，共享同一 runtime；(3) 新增前端动画/交互层（idle 行为、拖拽、情绪状态机），这是 my-agent 的空白区，需收紧范围防失控。

### 2026-07-04 主动性档位：定时主动搭话（复用现有 Scheduler）
**背景**：桌宠"活人感"的核心是主动性，但主动性做多深直接决定架构规模——从"纯被动等点击"到"感知屏幕/应用上下文智能搭话"是一条陡峭的复杂度曲线。
**决策**：做**定时主动搭话**档——桌宠按时间节奏（含一定随机性）主动开口，不做屏幕/应用感知。
**原因**：my-agent 已有 Scheduler 子系统（scheduled_tasks 表 + interval/cron + 触发 Agent Loop），主动搭话可直接复用，几乎零新增基础设施。既拿到"活人感"的关键体验，又避免新建感知层（截屏/窗口监听/OCR）这种高成本高风险模块。
**放弃的选项**：(1) 纯被动——没有主动性，活人感大打折扣；(2) 上下文感知主动——要新建屏幕/应用感知子系统，成本与隐私风险都高，超出比赛周期。

### 2026-07-04 优先级：先跑通形态闭环
**背景**：赛程假设偏紧，需要明确先做哪条线。
**决策**：优先**跑通形态闭环**——透明置顶桌宠窗能显示角色、能唤起聊天、聊天接通已有 agent 引擎、能收到主动搭话，先让"这是个活的桌面伙伴"整体成立。
**原因**：桌宠是"形态创新"作品，评审第一眼看的是形态是否成立、是否连贯。先有可跑通的端到端骨架，再往里填精致度（动画细节、情绪丰富度），风险最低。骨架不通，再精致的单点也拼不成作品。
**放弃的选项**：先打磨单点精致度（如高质量动画）——单点再好，形态不闭环就不是一个完整作品，比赛风险高。

### 2026-07-04 桌宠"身体"技术方案：序列帧动画 + CSS 辅助
**背景**：桌宠视觉实现有多条路线（Live2D / Spine / 序列帧 / Lottie / 纯 CSS+SVG / Rive），选型决定 gpt-image-2 要出什么素材、前端动画层怎么搭。已完成六方案调研对比。
**决策**：**序列帧动画（逐帧 PNG / sprite sheet）为主 + CSS transform 辅助**。
**原因**：
1. **与 gpt-image-2 最契合**——AI 只能出静态图，序列帧是唯一「直接吃 AI 静态图、无需建模绑骨、Electron 集成零门槛」的路径。让 AI「多出几张图」当帧，比「学一套绑骨软件把一张图撬活」省太多，是把 AI 出图能力直接变现的最短路径。
2. **两周可落地**——第一天即可跑通；无第三方授权/无原生依赖；纯 `<canvas>` 或 CSS `background-position` 播放，React 侧一个 `requestAnimationFrame` 循环即可。
3. **表现力够用**——idle 呼吸、眨眼、表情切换、点击反应、被拖拽全能做；Q 版桌宠 12–24fps 观感足够。
**关键落地技巧**：呼吸/待机用 CSS 整体缩放位移（近零成本）；眨眼/表情/动作用 gpt-image-2 出帧。为解决多次出图的**帧间一致性漂移**（脸/发色变），用 image-to-image / 局部重绘（inpainting）只改动作部位，保持主体不变——这是序列帧方案能稳落地的核心技巧。
**放弃的选项**：
- **Live2D**：表现力天花板最高，但要 PS 拆图层+补绘遮挡+Cubism Editor 绑骨 K 帧，学习曲线陡，会吃掉 3–5 天，且与 AI 出图优势不契合。除非已会，否则不在比赛里第一次学。（若后续有余力可作为加分升级项）
- **Spine**：编辑器付费 + 绑骨 + 学习成本，比赛不划算。
- **Lottie**：矢量动画需 After Effects 手做，与 AI 位图出图最错配。
- **Rive**：状态机交互是亮点，但仍要在编辑器里重建动画，发挥不出 AI 出图优势。
**待比赛提交前核实**（会变动，不影响本决策）：若最终改用 Live2D/Spine/Rive，需核对各自官网当前授权与定价条款。

### 2026-07-04 参赛作品最终定位：手机接入多 agent 的完整通道工具
**背景**：OpenClaw 研究完成，需确定参赛作品的精确形态。之前记录的方向 A（借 IM）在理解 OpenClaw 架构后重新评估。
**决策**：做**自建 Web App + 多引擎 Gateway 通道**，不借 IM。
- 手机端：Web App（浏览器打开即用，Gateway 托管静态页 + WebSocket）
- 服务端：Node.js + TypeScript，单进程单端口复用 WS + HTTP
- 多 agent = **多引擎接入**：Gateway 定义 AgentProvider 接口，对接多个 agent 后端（my-agent / OpenClaw / Claude 等），统一暴露给手机端
- 流式：WebSocket 事件流（agent delta）+ HTTP SSE（OpenAI 兼容）
**原因**：
1. Web App 零安装、跨平台、Demo 最直观——手机扫码即用，评审无需装 App。
2. 多引擎接入是差异化赢点：不是"又一个 chatbot UI"，是"统一入口操控多种 agent 引擎"——别人接 OpenAI，我们接任意 agent。
3. Node.js + TypeScript 与 OpenClaw/my-agent 同栈，参考代码可直接对照，参考价值最大化。
4. 自建通道（非借 IM）才能完全掌控流式体验、多 agent 路由、危险操作确认这些核心交互。
**放弃的选项**：
- 借 IM（方向 A）：交互受 IM 限制，流式体验差，多 agent 路由难表达。适合 MVP 验证但不适合参赛 Demo。
- 原生 App：体验最好但两周风险太高。
- Python/Go：与参考代码异构，对照成本高。

### 2026-07-04 通讯协议：参考 OpenClaw 的 WS JSON-RPC + 流式事件
**背景**：Gateway 与手机端的通讯协议需要定。
**决策**：采用 OpenClaw 风格的 WebSocket JSON-RPC 协议。
- 三种帧：`req`（请求）、`res`（响应）、`event`（事件推送）
- 连接握手：`connect` → `hello-ok`（带 agent 列表快照）
- Agent 运行两阶段：立即 ack + 流式 `agent` 事件（带 delta）+ 最终完成响应
- 同时提供 OpenAI 兼容 HTTP SSE 端点（`/v1/chat/completions?stream=true`）作为备选接入方式
**原因**：OpenClaw 的协议设计经过验证，两阶段运行模型天然支持流式，JSON-RPC 简单可调试。SSE 端点让标准 OpenAI SDK 也能接入，降低手机端开发成本。
**放弃的选项**：纯 HTTP 轮询（实时性差）、纯 SSE（双向通讯弱）、gRPC（浏览器不友好）。
